A repository using this rule enforces that pull request titles follow the [Conventional Commits](https://www.conventionalcommits.org) format.
Doing so helps to ensure that the purpose of a pull request is clear and consistent for humans and machines.

Specifically, keeping to the conventional commit format helps:

- Humans: it becomes easier to categorize and understand pull request purposes quickly
- Machines: automated tooling can parse those titles into semver-based releases

If a repository has this rule enabled, it's likely aiming for either or both of those benefits.

## Allowed Titles

This rule asks that titles be in either format:

```plaintext
type: body
type(scope): body
```

- `type`: the conventional commit type, such as `docs` or `fix`
- `scope`: an optional single sub-area, commonly a package name if a monorepo
- `body`: a lower-case description

Example acceptable titles include:

```plaintext
docs: mention 'rick' feature in README.md
feat: add optional new 'roll' option to API
fix(parser): don't throw error on consecutive semicolons
```

## Options

This rule accepts the following [rule options](/get-started#rule-options) to restrict which titles are allowed:

- `types`: an array of conventional commit types to allow instead of the [default known types](https://www.npmjs.com/package/conventional-commit-types)
  - Each type may contain ASCII letters, digits, and `_` characters
- `scopes`: an array of single scopes to allow; titles may still omit a scope
  - Each scope may contain ASCII letters, digits, spaces, and `_$@.-*/` characters

For example, this configuration only allows `docs`, `feat`, and `fix` types, with scopes that are either omitted or are `cli` or `parser`:

<Code
	code={getRuleWithOptions("pr-title-conventional", {
		scopes: ["cli", "parser"],
		types: ["docs", "feat", "fix"],
	})}
	meta="lang=yml"
	lang="diff"

### Subject Options

These options restrict the `subject` portion of a title, after its type and optional scope:

- `subject-case`: `"lower"` to ask that the subject not start with an upper-case letter
- `subject-trailing-punctuation`: `false` to ask that the subject not end with `!`, `,`, `.`, `:`, `;`, or `?`
- `subject-pattern`: a regular expression the entire subject must match
- `subject-pattern-error`: a sentence describing `subject-pattern` to report in place of the pattern itself

For example, this configuration asks for lower-case subjects without trailing punctuation, optionally prefixed with a bracketed list of rule names:

<Code
	code={getRuleWithOptions("pr-title-conventional", {
		"subject-case": "lower",
		"subject-pattern": "^(\\[[a-z\\-]+(, [a-z\\-]+)*\\] )?[a-z].+$",
		"subject-pattern-error": 'PRs for rules should begin with "[rule-name] ".',
		"subject-trailing-punctuation": false,
	})}
	meta="lang=yml"
	lang="diff"
	title=".github/workflows/octoguide.yml"
/>

:::note
`subject-case` compares the subject's first character, so subjects starting with a proper noun such as `README.md tweaks` are reported.
Repositories that want to allow those can use a `subject-pattern` instead.
:::

:::note
`subject-trailing-punctuation` intentionally allows a trailing `…`, which GitHub adds when it truncates a long commit message into a PR title.
:::
