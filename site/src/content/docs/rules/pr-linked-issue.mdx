A repository using this rule keeps to GitHub issues for discussing potential changes.
Most or all changes should be marked as approved in an issue before a pull request is sent to resolve them.

## Linking an Issue

To link a pull request to an issue:

1. Make sure there's an issue describing what you want to happen
2. Add text in the format `closes #...` or `fixes #...` in your PR, such as `fixes #123`

GitHub only links issues from closing keywords like `fixes #123` in pull requests that target the repository's default branch.
Pull requests that target other branches, such as stacked pull requests, can still have issues [manually linked from the pull request sidebar](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue#manually-linking-a-pull-request-to-an-issue-using-the-pull-request-sidebar) by anyone with write access.
Otherwise, this rule checks their pull request bodies for closing keywords:

- Issue references can be written as `#123`, `GH-123`, `owner/repo#123`, `owner#123` with this repository's owner, or a URL to the issue
- Links count by their URL rather than their text, so `fixes [the crash](https://github.com/owner/repo/issues/123)` refers to issue 123, while links to anywhere other than an issue are ignored
- Closing keywords in code or HTML comments, on a different line from their issue reference, or separated from it by formatting such as emphasis, are ignored
- Closing keywords for this repository must refer to an existing issue, not a pull request
  - If GitHub responds with an error other than not found, such as from rate limiting, the issue is assumed to exist
  - In forks, `#123`-style references to issues not found in the fork are assumed to be in its parent repository
- Closing keywords left unchanged from the pull request template, such as `fixes #000`, are ignored
- Closing keywords for issues in other repositories are assumed to refer to an existing issue

## Dependabot Security Alerts

Pull requests that address Dependabot security alerts don't need a separate issue.
You can satisfy this rule by including a link to the Dependabot alert in your PR body:

```
fixes https://github.com/owner/repo/security/dependabot/123
```

This recognizes that security vulnerability fixes often don't need the same discussion process as other changes.

## Why Require Issues?

Requiring all contributor pull requests address an open issue adds process to a repository.
Not all repositories prefer this.
Some prefer to instead make it as straightforward as possible to send a pull request, and then only move conversations to issues as needed.

The advantages of starting with issues are:

- Consolidation: most or all conversations are moved to a single place, the issue tracker
- Discoverability: it's much easier to search within just the issue tracker, rather than also looking through ad hoc pull request discussions
- Tracking: issues often use different their own sets of labels tailored to their conversations

Most importantly, if you're contributing to a repository with a contribution guide, please read and respect that contribution guide.
