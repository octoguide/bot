Force-pushing a pull request rewrites its history.
Once a pull request has been reviewed, rewritten history makes it harder for reviewers to see what changed since their last review.

Many repositories squash merge pull requests, so there's no need to keep a pull request's commits clean.
Pushing new commits on top of existing ones keeps each review's changes easy to find.
To bring in changes from the base branch, such as to resolve merge conflicts, merge the base branch in instead of rebasing onto it.

This rule reports when a pull request's latest commit was force-pushed by its author after the pull request was first reviewed.
Reviews from bots, such as automatic Copilot reviews, and from the pull request's author don't count.
Force-pushes by anyone other than the author, such as maintainers or stacking tool bots, are ignored.

## Running on Pushes

Pushes to a pull request fire the `synchronize` event, which OctoGuide's [default workflow](/get-started#installation) doesn't run on.
A pull request can't have been reviewed yet when it's opened, so with the default workflow, this rule only checks pull requests when their title or body is edited.
Its reports also stay until the next edit.

This rule needs `synchronize` in the workflow's `pull_request_target` types to check every push.
With it, a report is resolved as soon as new changes are pushed without force-pushing:

## Examples

<OctoGuideGitHubComment rule="pr-force-push-avoided">
	This pull request's latest changes were force-pushed after it was reviewed.
	This repository asks that pull requests not be force-pushed after they've been
	reviewed. Rewriting a pull request's history makes it harder for reviewers to
	see what changed between reviews. To resolve this report, push any further
	changes as new commits rather than force-pushing. There's no need to rewrite
	existing commits to keep them clean. If you need to resolve conflicts, merge
	the base branch in instead of rebasing onto it.
</OctoGuideGitHubComment>
